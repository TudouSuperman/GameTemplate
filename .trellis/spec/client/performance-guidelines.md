# 运行时性能规范

## 性能是设计约束

实现前先确认代码是每帧、每实体、每次命中、每个 UI 元素，
还是仅在初始化和生成时执行，并估算调用次数。

少量对象下功能正确，不足以证明高频路径在真实规模下可用。

## 热路径规则

- 高频路径避免 LINQ、每帧创建集合、重复 `GetComponent`、不必要的装箱、闭包、字符串格式化和高频日志。
- 所有权明确时复用集合，并在明确的生命周期节点清空。
- 大量 Entity、投射物、伤害数字和 UI 元素应优先考虑对象池、批处理和资源复用。
- 除非诊断开关已启用，否则正常高频路径中不要记录日志。

## 生命周期与状态语义

- 事件订阅、更新注册、异步任务和对象池激活，必须分别配对退订、注销、取消和重置。
- 保留所属系统的时间模型，不要未经确认混用秒、帧和 Tick。
- 使用批处理或缓存时定义失效和重置节点；过期缓存既是正确性问题，也是性能风险。
- UI 只负责表现，除非架构明确要求，否则不应建立第二套权威计算。
- 不得为了减少少量分配而破坏对象所有权、事件解绑、异步取消或对象池生命周期。

## 性能验证

性能验证应使用接近实际规模的场景，至少关注：

- CPU 帧时间
- GC 和托管内存分配
- 高频调用次数
- 网络或战斗 Tick 稳定性（适用时）
- 对象池循环
- 场景切换
- UI 启用和禁用
- 暂停与恢复
- 生成和销毁

没有 Profiler、测试数据或明确调用次数依据时，
不得把“性能更好”当作已验证结论。

## 示例

```csharp
// 正确：在初始化时缓存，生命周期结束时清理。
private Transform m_Target;

private void OnEnable()
{
    m_Target = GetComponent<Transform>();
}

private void OnDisable()
{
    m_Target = null;
}
```

不要在 `Update` 中反复调用 `GetComponent`、创建临时集合或输出调试日志。
