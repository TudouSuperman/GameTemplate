# 运行时性能规范

## 性能是设计约束

实现前先确认代码是每帧、每实体、每次资源加载、每个 UI 元素，
还是仅在初始化和生成时执行，并估算调用次数。

少量对象下功能正确，不足以证明高频路径在真实规模下可用。

## 热路径规则

- 高频路径避免 LINQ、每帧创建集合、重复 `GetComponent`、不必要的装箱、闭包、字符串格式化和高频日志。
- 所有权明确时复用集合，并在明确的生命周期节点清空。
- Entity 和 UI 元素需要频繁创建、销毁时，优先复用项目已有的引用池、对象池、Container 和资源生命周期入口。
- 除非诊断开关已启用，否则正常高频路径中不要记录日志。

## 生命周期与状态语义

- 事件订阅、更新注册、异步任务和对象池激活，必须分别配对退订、注销、取消和重置。
- 保留所属系统的时间模型；新增自定义更新频率前，先确认现有 Unity/GF 更新入口及其时间单位。
- 使用批处理或缓存时定义失效和重置节点；过期缓存既是正确性问题，也是性能风险。
- UI 只负责表现，除非架构明确要求，否则不应建立第二套权威计算。
- 不得为了减少少量分配而破坏对象所有权、事件解绑、异步取消或对象池生命周期。

## 性能验证

性能验证应使用接近实际规模的场景，至少关注：

- CPU 帧时间
- GC 和托管内存分配
- 高频调用次数
- 高频更新间隔的稳定性（适用时）
- 对象池循环
- 场景切换
- UI 启用和禁用
- 暂停与恢复
- 生成和销毁

没有 Profiler、测试数据或明确调用次数依据时，
不得把“性能更好”当作已验证结论。

## 示例

```csharp
// 项目现有模式：在初始化入口获取并缓存组件。
private Camera m_SceneCamera;

private void Awake()
{
    m_SceneCamera = GetComponent<Camera>();
}
```

不要在 `Update` 中反复调用 `GetComponent`、创建临时集合或输出调试日志。现有参考：`Client/Assets/Scripts/GameApp/Camera/SceneCamera.cs`。
